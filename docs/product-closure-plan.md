# Video2Notes 本地产品闭环实施规范

## 目标

Video2Notes 必须在 Windows 本机完成“导入来源 → 获取媒体 → 分析语音与画面 → 时间轴融合 → 生成笔记 → 局部返工 → 导出 Markdown/HTML/PDF”的完整闭环。默认流程面向首次使用者开箱即用；专业模式在同一套配置模型上开放精细参数，不维护第二套互相漂移的执行逻辑。

首要产物始终是可追溯的 Markdown。HTML 与 PDF 从同一个结构化笔记文档渲染，不能分别让模型自由生成而造成内容不一致。每条事实、截图和文字片段都应能回到统一媒体时间轴。

## 一、模型与协议闭环

供应商名称、传输协议、模型和处理角色必须分离：

- 供应商由用户命名，可以是官方服务、代理、本机服务或局域网服务。
- 协议模板只描述 URL、认证、请求和响应规则，不内置任何远程模型名。
- 模型由用户手工输入或通过协议的模型目录发现。
- 模型能力必须显式声明、发现或探测；不能仅凭供应商品牌或模型名猜测。
- 角色选择器只显示满足该角色全部能力要求、已启用且所属供应商可用的模型。不兼容模型不出现在下拉框内，同时在模型目录中说明缺少的能力。
- 后端对每次角色绑定再次校验，前端过滤不是安全边界。

首批协议适配：

1. OpenAI Responses
2. OpenAI Chat Completions
3. Anthropic Messages
4. Gemini generateContent
5. Gemini Interactions
6. Ollama Native Chat
7. OpenAI-compatible Chat/Responses（明确为能力子集）

OpenAI Audio、声明式 Custom HTTP、云端专用 OCR/ASR 属于扩展适配器；未完成执行适配的协议不得在 UI 中显示为“可运行”。Azure OpenAI 等只要使用上述协议和可配置认证头即可接入；需要动态签名的云平台协议另设适配器，不伪装成静态 API Key。

## 二、硬件余量与资源预算

推荐算法不能只看 CPU 型号、总内存和显卡总显存。每次打开设置页和提交任务前都应生成本机快照：

- CPU 逻辑核心数与当前负载
- 总内存、可用内存和内存压力
- GPU 名称、总显存、空闲显存、GPU 利用率和驱动
- FFmpeg 可用的硬件解码后端
- 数据盘剩余空间

用户设置的是“保留给其他程序的余量”，而不是直接承担所有底层参数。默认保留 CPU、内存和 GPU 余量，动态可用预算取总量上限与实时空闲量的更保守值。

引导模式提供三种资源倾向：

- 系统友好：优先保持前台应用流畅。
- 平衡：默认推荐，允许后台持续处理。
- 尽快完成：提高并发，但仍保留不可突破的安全余量。

专业模式开放：CPU worker、解码线程、GPU 阶段并发、OCR batch、ASR beam/batch/compute type、视觉粗扫与精扫帧率、分析宽度、远程模型并发、超时与重试、缓存上限、验证次数、截图预算等。所有覆盖值都有范围校验、恢复推荐值和风险提示。

## 三、引导模式与专业模式

两种模式只改变信息密度和可编辑范围，不改变用户已经选择的快速/平衡/高精度处理意图。

引导模式：

- 新任务只要求来源、处理意图和输出选择。
- 自动显示当前硬件下的推荐计划、预计耗时范围和余量说明。
- 自动选择已经配置且兼容的角色模型。
- Markdown 与基础 HTML 默认生成；PDF 和关键截图按用户选择。
- 缺少本地组件或模型时，提供应用内一键准备，不要求使用终端或手改 JSON。

专业模式：

- 完整显示来源身份、时间段采样覆盖、模型路由与 fallback。
- 显示实际资源预算、限制来源和每个执行参数。
- 支持对 ASR、OCR、视觉分析、融合文本或报告单独返工。
- 显示证据时间轴、置信度、运行指标和产物清单。

## 四、自包含运行时

便携版必须携带桌面程序、后端、FFmpeg、FFprobe、yt-dlp 以及 OCR/ASR 的代码运行时。大体积模型权重可由应用内组件管理器按用户选择下载到应用数据目录，但下载、校验、版本选择、启用、修复和卸载全部在 UI 内完成，不要求安装 Python、CUDA Toolkit、FFmpeg、浏览器或命令行工具。

组件状态至少区分：

- 已内置并通过自检
- 需要下载模型资源
- 正在准备
- 可更新
- 校验失败，可一键修复
- 当前硬件不适配，并给出替代方案

构建产物必须有文件清单、SHA-256、依赖版本与许可证；便携目录不可混入开发者 cookie、密钥、模型缓存、视频或任务数据。

## 五、统一 UI 与动效

默认使用完整亮色界面。字体优先高可读的 Windows 可变字体与中文 UI 字体，发布前补充许可明确的自托管字体资产；正文和表单不得依赖网络字体。

视觉系统使用统一的颜色、间距、圆角、控件高度、焦点环和状态语义：

- 正文/表单/按钮默认不少于 14px，次级说明不少于 12px。
- 页面、面板、控件使用分层圆角，不把所有元素做成胶囊。
- 成功、提示、警告和错误有不同文字与颜色语义。
- 常规动效为 140–320ms 的非线性缓动，只动画 transform 与 opacity。
- 禁止 transition: all 和持续的装饰动画。
- prefers-reduced-motion 下停用位移、旋转、脉冲和平滑滚动。

## 六、阶段验收

### 阶段 A：配置契约

- Registry v1 可无损迁移到 v2。
- 主流生成协议都有独立 adapter contract test。
- 所有角色始终显示，未绑定状态清楚。
- 角色下拉框内不存在不兼容模型。
- 密钥只存在 Windows Credential Manager，日志和导出配置不含密钥。

### 阶段 B：资源预算

- `/api/system` 返回总量、实时空闲量、用户余量和每种质量的推荐计划。
- 引导设置可持久化，重新启动后保留。
- 专业覆盖经过后端验证，越界配置不能保存。
- 推荐计划在内存或显存被其他程序占用时会保守降并发，而不是只看显卡型号。

### 阶段 C：产品 UI

- 默认引导模式可在三个主要决策内提交任务。
- 专业模式能编辑并解释全部执行参数。
- 800–1440px 宽度均可配置 Provider 和模型。
- 首次无 Provider、无模型、后端离线、依赖缺失都有明确下一步，不出现空白页。

### 阶段 D：自包含与端到端

- 一台未安装 Python/Node/FFmpeg 的 Windows 测试机可直接运行便携版。
- 应用内可以准备本地 ASR/OCR 资源并完成演示视频。
- 链接/本地文件至少各走通一次媒体获取、证据生成和 Markdown/HTML/PDF 导出。
- 便携版覆盖更新不会删除 AppData 中的任务、配置和凭据。
